# Loop Engineering — 迭代优化

基于stackwich的Loop层："循环工作在/loop上运行，失败循环最多2次，从不静默。"

## 核心理念

**有上限的迭代，从不静默失败。**

## 四阶段循环

```
任务定义 → 执行 → 自我反思 → 质量门控
    ↑                              ↓
    └──── 失败时最多循环2次 ←──────┘
```

### 阶段1：任务定义

```yaml
目标: 明确要优化什么
基线: 当前版本的质量评估
标准: 什么算"完成"
最大迭代: 2次（共3轮）
```

### 阶段2：执行

- 按计划执行改动
- 记录每次改动的内容和原因

### 阶段3：自我反思

每次执行后检查：

| 维度 | 检查项 |
|------|--------|
| 完整性 | 是否覆盖了所有要求？ |
| 正确性 | 有没有错误或遗漏？ |
| 质量 | 是否达到预期标准？ |
| 改进 | 有什么可以优化的？ |

### 阶段4：质量门控

```yaml
通过条件:
  - 所有检查项通过
  - 无明显错误
  - 达到质量标准

失败处理:
  - 第1次失败: 列出问题，回到执行
  - 第2次失败: 列出问题，升级到human
  - 从不静默失败
```

## 失败循环上限

| 迭代次数 | 处理 |
|---------|------|
| 第1轮 | 正常执行 |
| 第2轮 | 修复第1轮的问题 |
| 第3轮 | 最后尝试，必须成功或升级 |
| 第4轮 | ❌ 禁止，必须升级到human |

**核心原则：最多2次重试（共3轮），从不静默。**

## 四种改进模式

### 1. 渐进精炼
```
V1 → V2 → V3 → 完成
每次小改进，逐步逼近目标
```

### 2. 试错修正
```
尝试A → 失败 → 分析原因 → 尝试B → 成功
快速试错，从失败中学习
```

### 3. 对比择优
```
方案A + 方案B + 方案C → 选最优
并行生成多个版本，选最好的
```

### 4. 反馈驱动
```
输出 → 收集反馈 → 改进 → 再输出
基于外部反馈迭代
```

## Loop记录模板

```yaml
iteration: 1
changes: "修改了XXX"
result: "改进了YYY"
quality_score: 7/10
issues: ["问题1", "问题2"]
next_action: "继续优化" | "升级到human"
```

## 超限终止

当达到最大迭代次数时：

1. 停止迭代
2. 输出当前最佳版本
3. 列出未解决的问题
4. 升级到human决策

## 与其他Skill的协作

- **prompt-engineering** — 提供高质量的初始prompt
- **context-engineering** — 管理迭代过程中的上下文
- **harness-engineering** — 编排迭代中的工具使用
- **graph-engineering** — 多Agent协作时的迭代

## Present Results to User

```markdown
## 迭代结果

| 轮次 | 状态 | 质量分 | 说明 |
|------|------|--------|------|
| 第1轮 | ⚠️ | 6/10 | 发现2个问题 |
| 第2轮 | ✅ | 8/10 | 修复完成 |
| 第3轮 | ✅ | 9/10 | 优化完成 |

**结果：** 经过2轮迭代，质量从6分提升到9分。
```

## Pitfalls

1. **不要无限迭代** — 最多2次重试
2. **不要静默失败** — 每次失败都必须报告
3. **不要跳过反思** — 每轮都要自我检查
4. **不要降低标准** — 质量标准不能因迭代次数多而降低
5. **不要重复同样的错误** — 每次迭代必须有改进
